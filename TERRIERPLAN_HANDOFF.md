## What it is

A degree planning, HUB (BU's gen-ed) tracking, and course scheduling web app for Boston University students — the "(eventually)" on that last part is gone as of 2026-08-19, see Features below. Not affiliated with or endorsed by BU — an independent, community-made tool built with AI assistance.

Repo: https://github.com/BU-owo/TerrierPlan
Live: https://terrierplan.web.app/

**⚠️ `main` auto-deploys to the live site on every push** (see CI/CD below). There is no staging environment and no manual approval step — a bad push is live immediately.

## Stack

- Vite + React 19 (JavaScript, not TypeScript)
- Firebase Auth — Google Sign-In only in the actual UI (`LoginPage.jsx` renders just one button). The old handoff claimed email/password was also enabled; that may be true in the Firebase Console's auth provider settings, but nothing in the app UI exposes it.
- Firestore (Blaze/pay-as-you-go plan)
- Firebase Hosting, `dist/` as public dir, SPA rewrite-all-to-`index.html`
- `react-router-dom` v7 with `BrowserRouter` (`/login`, `/planner`, `/scheduler` — the last of which was still a redirect-to-`/planner` catch-all as of 2026-08-14, but is now a real route, see Features below; everything else still redirects to `/planner`)
- `@dnd-kit/core` for all drag-and-drop (semester board **and** dragging search results straight onto a semester column)
- `pdfjs-dist` (new) — client-side PDF parsing for the transcript importer, runs entirely in the browser, nothing uploaded to a server
- CI/CD: GitHub Actions, two workflows in `.github/workflows/` — one deploys `main` pushes straight to the live Hosting channel, the other builds a PR preview channel. Both run `npm ci && npm run build` with the six `VITE_FIREBASE_*` values injected from GitHub repo secrets.
- **New (2026-08-17): two standalone Python scraper scripts**, not part of the Vite app or its build — `scrape_bu_courses.py` (repo root) scrapes BU's course-bulletin pages for course number/name/prerequisites/description/HUB-area columns into a CSV; `scripts/scrape_bu_instructors.py` scrapes each course's own page for its per-section FALL 2026 schedule table (instructor, location, schedule text), importing shared URL-discovery helpers from the root script rather than reimplementing them. Neither is wired into `npm run build` or CI — run manually, output feeds the existing `scripts/import-*.cjs` Firestore importers.

## Firestore data model

`SCHEMA.md` at the repo root is still the intended source of truth, and it's mostly accurate — but I found one real gap in it (external credit `type`, below), so treat this section as the corrected version.

### `courses/{courseKey}` — reference data, ~8,939 docs
`courseNumber`, `name`, `prerequisites` (raw text), `description`, `hubUnits` (string array like `["SI1","CRI"]`), `lastScraped`. Publicly readable, write-locked to admin SDK only (`firestore.rules`: `allow write: if false`).

**New (2026-08-14):** `scripts/import-offering-data.cjs` merges historical-offering fields onto ~7,935 of those docs: `offeringPattern` (e.g. `"Fall"`, `"Alternating Spring"`, `"Not offered in 5 years"`), `offeredSeasons`, fall/spring/summer ratios, first/last offered year, `offeringDataUpdatedAt`. See SCHEMA.md for the full field list.

### `offeringHistory/{courseKey}` — new collection, not yet wired to a Firestore rule
Full per-term offering history (`{ term, year, season, sectionCount }[]`), written by the same import script. **Nothing in the app reads this yet, and `firestore.rules` has no `match` block for it** — unlike `courses`/`sections`/`bulletinPages`, it's currently unreadable from the client (Firestore default-denies unmatched paths). Not breaking anything today since nothing queries it, but it's a real gap to close (add a public-read rule matching `courses`) before building a feature that needs the full history rather than just the summary fields on `courses`.

### `sections/{term}_{classNbr}` — reference data, ~15,326 docs
Per-term section snapshot: `courseKey`, `term`, `credits`, `instructors[]`, enrollment/status fields, `notes` (free text). Imported once per term, not live. Publicly readable, same write lock as `courses`.

### `bulletinPages/{majorSlug}`
Legacy, effectively orphaned — the app's actual major/minor browser (`BulletinPanel.jsx`) is driven entirely by the static `src/data/bu-programs.js` list + a live iframe of the real bulletin page, not by this collection. Safe to ignore or delete.

### `siteStats/global` and `presence/{sessionId}` — new (2026-08-18), backing a vanity "X students have used TerrierPlan · Y online now" line in the new global footer (see Features below)
Both are approximate by design, not security-sensitive, and both are written **client-side directly from the browser** (`src/hooks/useSiteStats.js`) rather than through a Cloud Function — there is no Cloud Functions infrastructure in this repo at all (no `functions/` dir, no `firebase-functions` dependency, `firebase.json` only configures `firestore`+`hosting`). `siteStats/global.totalUsersEver` (number) increments by exactly 1 the first time a given browser is ever seen (gated by a `terrierplan_visitor_id` localStorage key, generated once and reused — this is deliberately a NEW key, not the pre-existing `terrierplan_session` one, which is actually the guest *plan* payload and gets deleted on sign-in, so it can't double as a "have we counted this visitor" flag). `presence/{sessionId}` docs (id = signed-in uid or the same visitor id) carry a `lastSeen` timestamp refreshed every ~30s while a tab is open, plus an `expiresAt` timestamp written for a Firestore TTL policy to eventually garbage-collect — **that TTL policy is not actually configured yet**, so stale presence docs currently just accumulate forever (harmless for the online-now count itself, which already filters by `lastSeen`, but unbounded storage growth). `firestore.rules` pins both collections' writes to their exact expected shape/delta (e.g. `totalUsersEver` may only be created at `1` or incremented by exactly `+1`) since there's no per-user auth scoping possible for a guest-writable collection like this — a motivated user could still inflate the numbers via devtools, which is an accepted tradeoff for a display-only counter, not a real security boundary.

#### `extraTerms[]` entry
`{ term: "Summer 2021", season: 'summer'|'winter'|'fall'|'spring', courseKeys: string[], isPostDegree?: boolean }`. These count toward HUB and credit totals but stay outside the 8-slot grid — rendered by `ExtraTermsPanel.jsx` below the semester board. `isPostDegree` fall/spring overflow terms (more than 8 semesters, or after a detected "degree awarded" line) also land here rather than being dropped.

#### `externalCredits[]` entry — SCHEMA.md's `type` list (`'ap' | 'transfer'`) is still missing `'ib'`; **the 2026-08-14 gap below is now closed for AP/IB specifically**
The 2026-08-14 version of this doc found that `'ib'` was fully modeled (`getIbHub`, every type check in `HubSidebar.jsx`/`ExternalCreditsPanel.jsx`) but **unreachable** — nothing in the app could ever produce a `type: 'ib'` credit, since the transcript parser only ever emitted AP-shaped rows. As of 2026-08-19 (`ExternalCreditsPanel.jsx`'s new `ExternalCreditChecklistForm`, behind a "+ Add External Credit" button), a student can **self-report AP or IB exam scores manually, with no transcript at all** — a checklist of every AP/IB subject (`AP_EXAM_SUBJECTS`/`IB_EXAM_SUBJECTS` in `src/data/apIbHubCredit.js`, now a real subject-by-subject chart with `getApHub`/`getApCredits`/`getApCourseInfo` and `getIbHub`/`getIbCredits`/`getIbCourseInfo`), check the ones taken, enter a score, and it resolves credits/HUB the same way an imported row would. This is how `type: 'ib'` actually gets created in practice today — **not** via transcript import, which is unchanged: `transcriptParser.js` still has no `INTERNATIONAL BACCALAUREATE` detection, and `transcriptMapping.js`'s `applyImport` still hardcodes `type: 'ap'` for every test-credit row it parses (neither file was touched by this work — verified via `git log`). So real IB credit printed on an actual transcript will still fail to parse or get mis-tagged as AP; only the *manual* path produces genuine IB entries. This same manual form only covers AP/IB — **transfer credit still has no manual-add path**, only transcript import, so Known Issue #6 below is partially, not fully, fixed.

Also new: a `manualCourses` field (string array) alongside the existing `manualCourseKey` — the same single-vs-multi split the auto-resolved side already had (a `courseKey` for a single-course match vs. a `courses` array when one exam resolves to a required multi-course bundle, e.g. Calc BC) now exists for the student's manual override too, so confirming "my advisor said this maps to two courses" doesn't have to force-fit into the single-`manualCourseKey` shape. `manualCourseKey`/`manualCourses` are mutually exclusive (see `normalizeExternalCredit` in `src/utils/externalCredits.js`).

BU policy, hardcoded as a comment in `apIbHubCredit.js` straight from BU's Advanced Credit Guide: **transfer credit never earns HUB, full stop**, even if it's equated to a BU course that normally carries HUB units. `HubSidebar.jsx`'s HUB-counting logic correctly skips `type === 'transfer'` entirely — verified, this is not a bug, it's intentional and matches BU policy.

### `users/{uid}/schedules/{scheduleId}`
**New (2026-08-17–19): actually in use now** — the Scheduler (see Features below) reads/writes this collection for real. Shape matches SCHEMA.md/the 2026-08-14 doc unchanged: `{ name, term, selectedSectionIds: string[], favorited: boolean, createdAt, updatedAt }`. Note there is **no per-section `locked` field on the saved doc** — locking a section into every generated combination is in-memory draft state only (`draftCourses` in `SchedulerPage.jsx`), not persisted; a saved schedule just freezes one specific combination's `selectedSectionIds`, with no memory of which of those were locked vs. picked freely.

## Firestore rules (`firestore.rules`)
`courses`/`sections`/`bulletinPages` — public read, no client write. `users/{uid}` and its `plans`/`schedules` subcollections — owner-only read/write (`request.auth.uid == userId`). The new `siteStats/global` and `presence/{sessionId}` collections (2026-08-18, see above) each got their own public-read, shape-pinned-write rule added. Otherwise no changes since the last handoff — notably, the `offeringHistory` collection (added 2026-08-09–13) still has no rule at all and remains unreadable from the client (see Known Issues below) — this was NOT fixed as part of the 2026-09-08 work, since nothing in this pass touched it.

A 3-step review UI (Upload → Review → Confirm) lets you resolve conflicts against courses already in your plan (skip/replace/keep-both), fill in AP scores for score-dependent exams, map transfer credits to BU equivalents (or explicitly save them as incomplete for later), and shows cumulative GPA/earned credits/points if found on the transcript footer.

Getting it onto the two full-height app-shell pages without an extra outer scrollbar required restructuring `App.jsx`'s layout: one `.app-shell` flex column now owns the `100dvh`, with the routed page as a flexible middle region and the footer as a fixed-height row under it, rather than each page's own root div claiming the full viewport height itself. Content: the disclaimer (reworded — now says "mostly vibe-coded" instead of "built with AI assistance"), a `mailto:` contact line, a Discord invite link, the site-stats line (see `siteStats`/`presence` above), and a "Need help?" button opening the same Help & Support modal described below.

Content: a support email `mailto:` link and a Discord invite; an earlier version had an in-app feedback form that opened a prefilled `mailto:` link, which was deliberately removed in favor of just the two direct links.
- **Scheduler** (`/scheduler`) — **new, 2026-08-14–19, no longer "deferred"** (see below): pick sections per course, generate every conflict-free combination, and manage the result, without leaving the grid.
  - Sections are grouped by BU's `component`/`componentLabel` field (Lecture/Discussion/Lab/etc., `sectionComponents.js`) — one required pick per distinct component per course, each course's own components checked against each other for conflicts too (a Lecture and a Lab for the SAME course aren't assumed conflict-free).
  - **Generation** (`scheduleCombos.js`): backtracking search over every checked/considered section, pruning a branch the moment two picks conflict (`sectionsConflict`, day+time overlap) rather than building the full cartesian product first; capped (`MAX_EXPLORED`/`MAX_RESULTS`) against pathological inputs, with the UI saying so explicitly rather than silently truncating. A section can be **locked** (forced into every generated combination, excluded from the pool other combos would otherwise cycle through) — this is the actual mechanism behind "pin a section," not a separate concept.
  - **"Why can't I generate a schedule" diagnostic** (`diagnoseNoSchedule`, new 2026-08-17): when generation comes back empty, re-runs it with each course dropped in turn to name which course's removal would unblock a schedule, instead of leaving the student to guess between a time restriction, a locked section, or a genuine clash between two specific courses.

  - **Saved schedules**: rename in place, a content-summary tooltip (course/section/time breakdown) on hover, favorite/star, delete — persisted to `users/{uid}/schedules` (see above) or `localStorage` for guests.
  - **Section-swap / ghost preview** (new, 2026-08-18): a button on each placed section (alongside pin/eliminate) opens a mode that overlays every OTHER available section for that same course+component on the weekly grid as translucent "ghost" blocks — using the course's existing stable color, dashed instead of solid, outlined in the existing conflict-warning color if picking that alternative would clash with something else already on the schedule. Clicking a ghost swaps it in; respects the existing time filter by default with a "show all" override. On the mobile single-column layout, the same feature is a tap-to-select bottom sheet (`SectionSwapSheet.jsx`) instead of overlapping ghost blocks, which wouldn't be legible on a narrow grid.
  - Also: a resizable preview pane (drag handle between the draft-builder and preview columns, width persisted to `localStorage`), and per-course custom colors (a 10-color palette chosen for pairwise OKLab separation in both themes, with a per-course override pickable from the grid's legend).
  - **Not built**: live seat availability, calendar export, and the "match against real-time registration" half of the original wishlist remain undone — this pass built the combination-generation/editing half, not the registration-adjacent half.
- **AP/IB self-report, no transcript required** (new, 2026-08-19) — see the `externalCredits[]` entry above for the full detail; summarized here because it closes a gap the 2026-08-14 pass flagged as real: `'ib'`-typed credit is now actually producible (manual checklist form), where before it was a modeled-but-unreachable type.

- **Degree-requirements engine** (new, 2026-08-09–13): `src/utils/requirementsEngine.js`'s `evaluateRequirementTree` walks a per-major requirement JSON (`src/data/requirements/<school>/<major-slug>.json`, e.g. `cas/computer-science-ba.json`, `cas/biochemistry-molecular-biology-ba.json`) against the plan's flat courseKey list — UI-agnostic, consumed by both the compact sidebar tab and the new full-screen view. Supports plain COUNT pools, and a SEQUENCE_GROUP node type that treats a fixed multi-course bundle (e.g. a CHEM sequence, or a two-course elective pair) as one slot rather than double-counting each course. ## What the two unclear commit messages actually did

**"yml something?" (`2ac6f6d`)** — edited both `.github/workflows/firebase-hosting-*.yml` files to inject the six `VITE_FIREBASE_*` secrets as `env:` vars on the `npm ci && npm run build` step, for both the merge-to-`main` deploy and the PR-preview build. Before this, the CI-built bundle had no Firebase config baked in at all (Vite inlines `import.meta.env.VITE_*` at build time, and nothing was setting those in the runner) — so any deploy through GitHub Actions prior to this commit would have shipped with `undefined` `apiKey`/`projectId`/etc., breaking Auth and Firestore entirely on the live site. This is also incidentally the commit that makes "main auto-deploys to the live site" actually functional and dangerous, since it made the CI deploy produce a *working* build.

**"embed thing for discord" (`2aa42f4`)** — added Open Graph (`og:title`, `og:description`, `og:image`, etc.) and Twitter Card meta tags to `index.html`, plus a plain `<meta name="description">`. Purely for link-preview cards when the URL is shared in Discord/Slack/iMessage/etc. — no functional/app behavior change.

## Environment/infra gotchas (carried forward, still true as of this rewrite)

- `.env.local` and the Firebase service-account key JSON are both gitignored and must be manually recreated on every new machine; `.env.example` is the template for the former.
- Firebase CLI (`firebase init`) walks **up** the directory tree looking for an existing `firebase.json`/`.firebaserc` — always confirm `pwd` is the actual repo root before running Firebase CLI commands.
- Firestore composite indexes are NOT needed for single-field `orderBy`+`startAt`/`endAt` prefix queries (confirmed still true — `firestore.indexes.json` is empty: `{"indexes": [], "fieldOverrides": []}`).
- `firebase-admin` v12+ API shape: `admin.credential` → `applicationDefault()` directly; `admin.firestore()` → `getFirestore()` from the `firebase-admin/firestore` subpackage; same for `FieldValue`. (This is exactly the distinction that makes the stale `.js` import scripts, above, broken.)
- Firestore Spark (free) plan's 20,000 writes/day quota was exceeded once during the initial bulk course+section import, requiring the upgrade to Blaze (still effectively free at this app's usage level).
- Import/patch scripts in `scripts/` need `GOOGLE_APPLICATION_CREDENTIALS` pointing at a service-account key file kept **outside** the repo folder.
